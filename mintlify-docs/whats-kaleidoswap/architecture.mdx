KaleidoSwap is vertically integrated: a single SDK powers every client we ship and every third-party integration, so each surface talks to the same swap engine, the same protocol adapters, and the same liquidity. Adding a protocol once makes it available everywhere; adding a client costs no new protocol work.

This page walks the stack from the top down. For the protocols themselves and why hash-locked contracts make cross-layer trades possible, start with [How It Works](/whats-kaleidoswap/background). For the broader multi-protocol thesis behind this design, read [Solving Bitcoin's L2 liquidity problem](https://kaleidoswap.medium.com/solving-bitcoins-l2-liquidity-problem-kaleidoswap-s-multi-protocol-dex-layer-0725b26f8de4).

## The stack

| Layer | What lives there |
|-------|------------------|
| **Clients & integrators** | Desktop App, Browser Extension, Mobile, Web App, CLI — plus third-party wallets, neobanks, payment processors, and AI agents |
| **Integration layer** | `kaleido-sdk` for swaps and market data; `wallet-engine` for wallet primitives across protocols |
| **Protocol layer** | One adapter per Bitcoin Layer, behind a single contract |
| **Liquidity layer** | The RFQ engine, the KaleidoSwap LSP today, external market makers from 2027 |
| **Intelligence layer** | KaleidoMind for local reasoning, KaleidoAgent for autonomous execution |
| **Settlement** | Bitcoin — where every layer above anchors |

The desktop app, SDKs, CLI, wallet engine, and MCP/AI tooling are open source (MIT) and inspectable on [GitHub](https://github.com/kaleidoswap); the browser extension and the maker-side RFQ engine are not public today.

## Protocol layer

Every Bitcoin Layer ships its own SDK, address formats, and quirks: channel liquidity here, boarding transactions there, static receive addresses somewhere else. Left unmanaged, that becomes a protocol check on every screen of every app.

Instead, each protocol implements **one adapter contract**: connect, list assets and transactions, create and decode invoices, send, receive, and optionally quote and execute swaps. Differences between protocols live as **data** in a capability manifest, not as branches in application code. The router and the UI read that manifest and never special-case a protocol by name.

The practical consequences:

- **Adding a protocol touches one adapter** and one manifest entry — never another protocol's path.
- **Clients call one API**, never a protocol SDK directly, so behaviour is consistent across Desktop, Extension, and Mobile.
- **The router picks the rail.** Given a destination — a Lightning invoice, a Bitcoin address, an RGB invoice, a Liquid address — it resolves which protocols can pay it and which is best.
- **One receive QR** can carry several protocols at once, so any wallet can pay it while KaleidoSwap wallets read the richer parameters.

## Swap engine

Swaps use a **Request for Quote** model settled by hash-locked contracts. The maker prices the trade; Lightning carries it; the shared preimage makes it atomic.

![Diagram of desktop, browser, and extension clients connecting to an RGB Lightning Node and a Lightning Service Provider, both linked to a chain of hash-locked blocks representing Bitcoin settlement](/assets/images/overview/architecture-overview.png)

On the shipped BTC ↔ RGB path, the flow is:

1. The taker streams quotes from the maker over WebSocket and receives an `rfq_id` with each one.
2. `POST /api/v1/swaps/init` locks the rate and returns a `swapstring` and a `payment_hash`.
3. The taker's RGB Lightning Node whitelists the `swapstring`, authorising it to route through the node.
4. `POST /api/v1/swaps/execute` starts the HTLC.
5. Lightning routes it: the maker reveals the preimage to claim one leg, which simultaneously releases the other.
6. If either side stalls, the timelocks expire and both sides recover their own funds.

The taker's node is the one holding keys and validating state throughout — the maker never takes custody. Full endpoint reference and sequence diagram: [Atomic Swap Protocol](/api-reference/swap-protocol).

<Note>
  Atomicity depends on both layers having a native hashlock. See [Where atomicity holds](/whats-kaleidoswap/background#where-atomicity-holds) for what that rules in and out today.
</Note>

## Liquidity layer

### Lightning Service Providers

LSPs make Lightning usable without manual channel operations. In the architecture they:

- **Provide liquidity** — open channels with inbound capacity, optionally pre-loaded with an RGB asset
- **Route payments** — find paths for both payments and swap legs
- **Act as counterparty** — locking the other leg of a swap

### RGB-LSPS1

KaleidoSwap implements the RGB Lightning Service Provider Specification, extending the standard LSPS1 channel-ordering flow to assets:

- **Standardised interface** — one API shape for LSP interactions
- **Asset allocation** — specify RGB assets when ordering a channel
- **Swap support** — atomic swap coordination built into the same surface
- **Fee transparency** — costs stated before you commit

See [RGB LSPS1 APIs](/api-reference/rgb-lsps1-apis) for the endpoints.

### Market makers

The RFQ engine is designed for competition on the maker side. Today the KaleidoSwap LSP bootstraps liquidity itself. From 2027, external market makers connect through the same interface and compete on spread.

## Client architecture

### Non-custodial design

Everything that touches keys runs on your device. Clients hold or drive the wallet locally, validate state themselves, and talk to makers and LSPs only over the network interfaces above. No third party has access to your funds at any point in a swap.

- **Your keys, your coins** — private keys never leave your device
- **Encrypted storage** — sensitive data encrypted at rest with your password
- **No custody** — makers and LSPs are counterparties, never custodians
- **Client-side validation** — you validate RGB state yourself rather than trusting a server

### Protocol coverage per client

| Client | Protocols | Wallet model |
|--------|-----------|--------------|
| **[Desktop App](/desktop-app/getting-started/introduction)** | Bitcoin L1, Lightning, RGB on Lightning | Drives a full RGB Lightning Node — local, Docker, or remote |
| **[Browser Extension](/extensions/introduction)** | Bitcoin L1, Lightning, Spark, Arkade, Liquid, node-less RGB-L1, optional RGB Lightning Node | One recovery phrase derives every protocol account |
| **[CLI](/cli/introduction)** | Bitcoin L1, Lightning, RGB on Lightning | One-command local node via Docker |

### Component layers

Inside a client the separation is the same regardless of platform:

1. **UI layer** — the interface, per platform
2. **Business logic** — state management and workflow orchestration
3. **Protocol layer** — `wallet-engine` adapters and the cross-protocol router
4. **Network layer** — node RPC, maker APIs, LSP integration, P2P connections

## Security model

<Steps>
  <Step title="Bitcoin base layer">
    Final settlement and security anchoring on the Bitcoin blockchain
  </Step>

  <Step title="Layer protocols">
    Hash-locked contracts and timelocks, so a failed swap refunds rather than half-executes
  </Step>

  <Step title="Asset overlay">
    Client-side validation of RGB state, preventing invalid or double-spent transfers
  </Step>

  <Step title="Application layer">
    Local key management, encrypted storage, and explicit confirmation before any spend
  </Step>
</Steps>

### What trustless means here

- **No counterparty risk** — on atomic paths the swap completes on both sides or neither
- **No custodians** — you keep your keys and your assets throughout
- **Cryptographic guarantees** — enforced by timelocks and preimages

## Settlement characteristics

Different layers make different trade-offs, which is why the stack uses several. There is no layer that is fastest, cheapest, and most final at once.

| Layer | Settles as | Native hashlock | Finality | Typical cost |
|-------|-----------|-----------------|----------|--------------|
| **Bitcoin L1** | An on-chain transaction | Yes (Bitcoin consensus) | 10–60 minutes | Prevailing fee rate |
| **Lightning** | A channel state update | Yes (Bitcoin consensus) | Seconds | Satoshis |
| **RGB** | A commitment inside a Bitcoin transaction or channel update | Yes (Bitcoin consensus), on Lightning | Follows the layer it rides on | Included in the anchor |
| **Spark** | A statechain key-share rotation; the on-chain UTXO never moves | Yes (layer trust model) | Sub-second, once operators delete the old key shares | Free in-network; Bitcoin fees on entry and exit |
| **Arkade** | A VTXO transfer, batched on-chain via a commitment transaction | Yes (layer trust model) | Instant preconfirmation, Bitcoin finality at batch settlement | Amortised across the batch |
| **Liquid** | A federated sidechain transaction | Yes (layer trust model) | ~2 minutes, at two confirmations | From 0.1 sat/vB, paid in L-BTC |

Lightning is where trading happens because it settles in seconds at negligible cost; Bitcoin L1 is where positions come to rest. The hashlock column is what decides whether a leg can be atomic, and under whose guarantee — see [Where atomicity holds](/whats-kaleidoswap/background#where-atomicity-holds).

## RGB asset interfaces

RGB defines several asset interfaces, previously known by their schema numbers. The wallet supports all four; trading covers NIA assets today.

| Interface | Formerly | What it is | Supported |
|-----------|----------|------------|-----------|
| **NIA** | RGB20 | Non-Inflatable Asset — fixed-supply fungible tokens, used for stablecoins like USDT and XAUT | Yes |
| **IFA** | — | Inflatable Fungible Asset — fungible tokens the issuer can mint or burn | Yes |
| **UDA** | RGB21 | Unique Digital Asset — non-fungible, one-of-a-kind assets | Yes |
| **CFA** | RGB25 | Collectible Fungible Asset — collectibles with richer media and metadata | Yes |

Definitions for each term are in the [Glossary](/whats-kaleidoswap/glossary#bitcoin-layers-%26-assets).
