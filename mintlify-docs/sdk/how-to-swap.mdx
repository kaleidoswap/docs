Every HTLC swap runs through the same stages. The details differ by [swap type](/sdk/swap-types), but what your app must do at each stage does not.

<Steps>
  <Step title="Pick a route">
    Read the pair catalogue for the swap type (`submarinePairs()`, `reversePairs()`, `chainPairs()`), check the amount against the card's `limits`, and show the user its fees and rate. Keep the card's `hash`.
  </Step>
  <Step title="Derive key material">
    Take the next unused index from your persisted counter and derive the swap key (and, for reverse and chain swaps, the preimage) with `SwapMasterKey`. See [Keys and recovery](/sdk/keys-and-recovery).
  </Step>
  <Step title="Create and verify">
    Call `createSubmarineSwap`, `createReverseSwap`, or `createChainSwap` with your public key and the card's `pairHash`. The SDK rejects a response whose script, address, timeout, or invoice hash does not match what you asked for. Rebuild the `SwapScript` from the response with your own key.
  </Step>
  <Step title="Persist before you move money">
    Store the swap ID, the index, the maker URL, and the full create response, including `swapAuth`. Serialize with `toJson`, not `JSON.stringify`, because TypeScript responses carry `bigint` amounts.
  </Step>
  <Step title="Fund or pay">
    Fund the lockup address with exactly the expected amount (submarine, chain), or pay the invoice (reverse). Your wallet does this; the SDK holds no funds.
  </Step>
  <Step title="Track status">
    Subscribe to the swap over WebSocket, or poll `swap(id)`.
  </Step>
  <Step title="Claim or refund">
    Claim once the maker's lockup is confirmed (reverse, chain). Refund if the swap fails or expires (submarine, chain). See [Claims and refunds](/sdk/claims-and-refunds).
  </Step>
</Steps>

## Tracking status

### WebSocket

The maker streams status updates on `/v2/ws`. Run the socket loop, subscribe to each swap, and read updates as they arrive.

<CodeGroup>
```typescript TypeScript
import { SwapWsApi } from "@kaleidorg/swap-sdk";

const ws = new SwapWsApi("wss://maker.signet.kaleidoswap.com/v2/ws");
void ws.runWsLoop();
await ws.subscribeSwap(swap.id);

const updates = ws.updates();
for (;;) {
  const update = await updates.next();
  console.log(update.id, update.status);
  if (update.status === "invoice.settled") break;
}
ws.close();
```

```python Python
ws = client.ws()
asyncio.create_task(ws.run_ws_loop())
await ws.subscribe_swap(swap.id)

updates = ws.updates()
while True:
    update = await updates.next()
    print(update.id, update.status)
    if update.status == "invoice.settled":
        break
await ws.shutdown()
```
</CodeGroup>

A dead socket reports no error, which matters most on mobile after the app is backgrounded. Check `isConnected()` (`is_connected()` in Python) and fall back to polling.

### Polling

`client.swap(id)` (`get_swap` in Python) returns the current status and the maker's audit events for the swap. Poll it on resume, after a reconnect, and anywhere you cannot hold a socket open.

## Status names

| Status | Meaning |
|---|---|
| `swap.created` | The swap exists; nothing has been paid or locked yet |
| `invoice.set` | A submarine swap has its invoice |
| `transaction.mempool` | A lockup transaction is in the mempool |
| `transaction.confirmed` | The lockup has confirmed |
| `invoice.pending` | The maker is paying the invoice (submarine) |
| `invoice.paid` | The maker paid the invoice (submarine) |
| `transaction.server.mempool` / `transaction.server.confirmed` | The maker's lockup on the destination chain (chain swaps) |
| `transaction.claim.pending` | A cooperative claim is in progress |
| `transaction.claimed` | The lockup has been claimed; the swap succeeded |
| `invoice.settled` | The hold invoice settled; the reverse swap succeeded |
| `swap.expired` | The swap expired before it was funded |
| `invoice.expired` | The invoice expired unpaid |
| `invoice.failedToPay` | The maker could not pay the invoice; refund your lockup |
| `transaction.lockupFailed` | The lockup was wrong (amount or asset); refund it |
| `transaction.failed` / `transaction.refunded` | The maker's side failed or was refunded |

Treat the maker's status as information, not proof. Before you sign a claim, check the lockup transaction on your own chain backend. Before you refund, check the chain tip against the swap's timeout.

## Deadlines

- **Refunds** become possible through the script path once the lockup chain reaches the swap's `timeoutBlockHeight`. Before that, a refund needs the maker's cooperation.
- **Claims** must confirm before that same timeout, or the maker can refund the lockup. The reconciliation helpers stop by default 6 blocks before the deadline on Bitcoin and 60 on Liquid.
- **Chain swaps** have two timeouts: the lockup side for your refund and the claim side for your claim.

## Recovering after a restart

If your app loses its local state, `SwapMasterKey.restore(client)` finds every swap the maker has seen for your swap mnemonic, including the ones still owed a claim or refund. `SwapScript.fromRestored` rebuilds each script without the original create response. See [Keys and recovery](/sdk/keys-and-recovery#restoring-swaps).
